# 调试器页（`#dbg`）—— 零安装的极简调试前端

异常现场使用右侧「异常」页签，支持 Cortex-M3/M4/M7 和 RV32 的只读诊断与报告；操作和证据边界见 [异常诊断与采集质量](diagnostics.md)。

> 目标：**不装任何软件**，在浏览器里对目标做平时最常用的那几件事 ——
> 暂停 / 继续 / 单步 / 复位、看改寄存器、看改内存、下硬件断点、按符号名看变量、
> 浏览**符号列表**、把变量丢进**监视窗口**、停下来显示**当前源码行**，顺手在旁边看 RTT 的 printf。
>
> 2026-10 补齐了"手感"这一层（对齐 MDK/Ozone 的日常动作）：
> **按 `文件:行` 下断点**、**源码级单步**（跳过 `n`/F10 · 进入 `si`/F11 · 跳出 `fin`/Shift+F11）、
> **运行到光标**（源码行双击）、**结构体/数组的树形监视**（含位域）、以及 PC 的"行内偏移"显示。
> 明确**不做**：反汇编、局部变量（DWARF 表达式求值）、调用栈回溯、RTOS 感知、多核、软件断点。
>
> 入口：`index.html#dbg`（或双击 `start-web.bat` 后点「调试器」）。

自测：`make test-dbg`（纯 Node，**240 项**）、`make test-dbg-page`（CDP 真页面，**140 项**）、
`make test-dbg-hw`（真探针 + 真目标板的冒烟：连接 → 读 IDCODE/寄存器/内存 → 暂停/单步/继续 →
试一个断点再删掉 → 符号列表/监视/源码行；**只读为主**，跑完把目标放回运行状态）。
> ⚠️ 真机那条的前提是**探针没被别的程序占着**：同一个浏览器的别的页签、或另开的浏览器
> （Chrome/Edge）里还连着探针时，`claimInterface` 会报 `Unable to claim interface` ——
> 脚本会明确提示并跳过，不会假装成功。
>
> ⚠️ 真机冒烟会**先「暂停」再读寄存器**（脚本自己保证幂等）：目标可能是上一次冒烟放跑的运行状态，
> 不停下来就读不到寄存器。单步那一条若目标正卡在 `b .`（HardFault 死循环，PC 处机器码 `fe e7`），
> 脚本打印诊断并**跳过**而不是判失败 —— 那是目标的状态，不是调试链的锅。
>
> ⚠️ **别拿 A 芯片的 ELF 去调 B 芯片**（2026-10 踩过）：页面的符号/行号/地址全来自载入的 ELF，
> 而寄存器/内存来自**实际连着的那块板**。两者不一致时的现象很迷惑（PC 落在"合理的"源码行、
> 断点"下成功了"却永远不命中、读 H7 专属寄存器报 FAULT）。判别方法：看日志里的 `IDCODE`
> （Cortex-M3/M4 的 SW-DP 是 `0x1BA01477`，H7 是 `0x6BA02477`）和 `FPB 比较器个数`
> （M3/M4 常是 6 个、M7 是 8 个）。

## 2. 底座是复用的，没有另起一套

`app/rtt/dap-webusb.js` 的 `WebUsbDapProbe` 早就把最难的部分写完了：
`halt/run/isHalted/_dhcsr`、`regRead/regWrite`（DCRSR/DCRDR）、`readMem/writeMem`、
`_targetInit`（SWJ 激活 + DP 上电 + CSW 试配）。调试页只是在它上面加了三件事：
**硬件断点（FPB）**、**单步**、**抢占纪律**。

## 3. 三条硬约束（踩过的，别改回去）

### 3.1 SWD 时钟：默认 10 MHz，PPB 读不灵就自动退回 1 MHz
`DHCSR/DCRSR/DCRDR`、`FPB`、`AIRCR` 都在 `0xE0000000` 这一片（PPB）。这颗探针固件**历史上有**
"时钟偏高时 PPB 读回 0"的毛病（烧录 / 读 IDCODE 那边一直强制 1 MHz），所以页面早期把默认压到 1 MHz。

**2026-10-02 真机复测（akaLinkPro + STM32F103ZE）**：10 / 20 / 30 MHz 下 DHCSR、FPB、PC、RAM 全部正确；
读 32 KB 从 1 MHz 的 ~330 ms 降到 10 MHz 的 **85 ms（375 KB/s）**、20 MHz 的 66 ms（488 KB/s）。
于是把默认改成 **10 MHz**（下拉给 5/10/20 MHz 与 1 MHz 保守档），并加一道兜底：

* `DebugSession.verifyClock()` —— 连上后立刻连读 3 次 DHCSR，**回 0 / 回 0xFFFFFFFF / 三次不一致**就判定
  这个档位读 PPB 不可信 → 用 `SWJ_Clock` 退回 **1 MHz**、把证据写进日志、下拉框同步改成 1000（不静默降级）。
* 假目标里有 `ppbGarbage` 开关专门模拟"坏探针"，自测把这条回退路径也跑一遍。

> 所以：**寄存器/断点不灵时先看日志有没有那行"已自动退回 1 MHz"**；没有的话再怀疑接线、BOOT0、电源。
> 内存 / 监视 / RTT 通路在高时钟下本来就是好的。

### 3.2 命中断点后"继续"必须先跨过它
FPB 是"取指地址命中就停"，命中后 PC **停在断点那条指令的地址上** ——
直接 `C_HALT=0` 让它跑，它会立刻再命中一次，用户看到的是"点了继续没反应"。
`session.cont()` 的做法与 gdb/pyOCD 一致：**临时摘掉那个比较器 → 单步一条 → 装回比较器 → 继续**。
`step()` 里同样要摘（否则"在断点上单步"原地不动）。

### 3.3 CFBP 的字节顺序（查过权威实现，不是猜的）
`DCRSR.REGSEL = 0x14` 返回一个打包值：

| 字节 | 寄存器 |
|---|---|
| `[7:0]` | PRIMASK |
| `[15:8]` | BASEPRI |
| `[23:16]` | FAULTMASK |
| `[31:24]` | CONTROL |

依据 OpenOCD `src/target/armv7m.c`（`*offset = arm_reg_id - ARMV7M_PRIMASK`，按 `offset*8` 取字节）
与 pyOCD（`(val >> ((reg & 3) * 8)) & 0xff`）。写单个特殊寄存器走**读-改-写**，别把兄弟字节冲掉。

## 4. FPB（硬件断点）要点

* 寄存器：`FP_CTRL=0xE0002000`（bit0 ENABLE、bit1 KEY **必须同时置 1**）、`FP_COMPn=0xE0002008+4n`。
* 比较器个数：`((ctrl >>> 8) & 0x70) | ((ctrl >>> 4) & 0x0f)`；版本 `1 + (ctrl >>> 28)`（0→rev1、1→rev2）。
  真机 Cortex-M7 读到 `0x82` → **8 个**。
* 编码（照抄 pyOCD `fpb.py`，真机久经考验）：
  * rev1：`comp = (addr & ~3) | BP_MATCH | 1`，`BP_MATCH` = 上半字 `2<<30` / 下半字 `1<<30`；
    **只能匹配 `0x20000000` 以下**（所以 H7 的 QSPI 代码 `0x9…` 打不了）；解码时 bit1 要从 `BP_MATCH` 还回来。
  * rev2：`comp = (addr & ~1) | 1`，地址不限。
* 删断点 = 往比较器写 0；最后一个断点删掉后 `FP_CTRL = KEY|0`（关掉整个 FPB）。
* 写完全部比较器**必须回读对账**：这颗探针的 PPB 写偶发不落地，断点静默失效最难查。
* 接手时**清掉上一次会话残留的比较器**（标准调试器行为），否则目标会"莫名其妙停住"。

## 5. 会话与运行流程

```
连接   → 请别的页签让出探针（probe-bus）→ 停掉「RTT 转发」的探针桥（HID 0x31 action 0）
       → 关掉本页签残留的探针句柄 → WebUsbDapProbe.open(clockKhz=1000)
       → 读 DHCSR 判断"在跑/停住" → 读 FP_CTRL 得到断点容量
继续   → 先清 DFSR → （PC 在断点上就先单步跨过）→ 写 DHCSR = 0xA05F0001
暂停   → 写 DHCSR = 0xA05F0003
单步   → 写 DHCSR = 0xA05F000F（DEBUGEN|HALT|STEP|MASKINTS）
         然后**先看到 S_HALT 变 0、再看到它变 1**；只等"=1"会立刻返回（等于没等）
复位   → 写 AIRCR.SYSRESETREQ（0x05FA0004），**不用探针的 nRESET 引脚**
         （本机好几块板没把 NRST 接给探针，"拉复位"看着成功其实没动）
```

界面侧还有一个**观察循环**（`view._watchLoop`）：点「继续」之后每 150 ms 读一次 DHCSR，
停住时刷新寄存器、报"命中断点/已停止"，并在开着 RTT 时顺手泵一次 RTT 上行。
短等待一律用 `core/pace.js` 的 `waitMs`（`setTimeout` 在页面不可见时会被钳到 ≥1 s）。

### 5.1 🚨 SWD 必须串行化（2026-10-02 真机定因）
**一条 SWD 链路上任何两次操作交错都会读出垃圾。** 实测：观察循环开着的时候，从外面连读 PC
**100 次里 18 次是废值**（`0x0` / `0x1` / `0x999` / `0x40011000`…），停掉循环后 100 次全对；
1 MHz 与 10 MHz 都一样 —— 所以**不是时钟问题，是并发问题**（连续读 DCRDR 前被别人的 DCRSR 插了一脚）。
界面上看到的就是"寄存器表偶发乱码、点了没反应"。

规则（改代码时守住）：

| 谁 | 用哪个 | 行为 |
|---|---|---|
| 用户动作（`view._act`）、命令行（`view.runLine`）、自动化脚本 | `session.exclusive(fn)` | 排队执行，整段独占 |
| 后台轮询（观察循环、RTT 泵） | `session.tryExclusive(fn)` | **正忙就跳过这一拍**（不排队、不堆积） |

两者**不许互相嵌套**（`exclusive` 不可重入，嵌套会死锁）。真机脚本（`dbg-hw.mjs`）开头会
`_stopWatch()` —— 脚本自己独占，别让页面的轮询插进来。

## 6. 假目标（`app/dbg/mock.js`）—— 自测的"标准答案"

没有硬件也能把整条链跑通，靠的是这个假目标。它刻意**照真硬件的行为**建模，
下面两条一旦偷懒，测试就会"全绿但线上全错"：

1. **读 DHCSR 不能回显 DBGKEY(0xA05F)**：钥匙只在**写**的时候给。把 `0xA05F` 或进读数会让
   bit17（S_HALT）恒为 1 → "目标明明在跑、读回来永远是已停止"。（本仓真踩过。）
2. **单步要能看到 S_HALT 的 0→1**：上层就是靠这个过程判断"这一步真的执行了"。

另外：一次字读的 4 个字节必须返回同一个值（上层是逐字节读的，每次重新采样会拼出假状态）；
FPB 比较器用**真的** `bp.js` 编解码（编码写错 → "断点永远不命中" → 测试变红）；
RAM 里放了一个结构合法的 **RTT 控制块**（`0x20000100`），跑起来会往环里写
`[dbg] tick N @0x…`，页面上的「RTT 输出」因此也能被自测覆盖。

## 7. 界面约定

> 版式（2026-10-02 照 Ozone 的意思重排，用户点名要求）：
> **左边一列** = 源码（上，默认占大头）+ 命令行（下，默认 `38%`），中间一条**可拖的横分隔条**；
> **右边一条「局部 tab」面板**顶到满高，四个 tab = **寄存器 / 内存 / 变量 / RTT** 一次只显示一个 ——
> 不再把四块平铺成小格子（那样每块都太小）。左边与右边之间还有一条**可拖的竖分隔条**。
> 两处尺寸都记在 localStorage（`dbg.dockW` / `dbg.termH`），tab 选择记在 `dbg.dock`。
> 窗口窄于 1240px 时右侧面板自动折到下面（仍是一整条 tab 面板）。

* 寄存器表（**寄存器 tab**）：每行一个输入框，**回车即写**（读回不一致会黄字提醒；有些位是只读的）。
  与上次相比**变了的值**整行标黄。PC/LR 那一行还带 `函数+偏移` 与 `文件:行`。
* 内存（**内存 tab**）：地址 + 长度（1~1024）→ hexdump；勾「可写」后**点某个字节**会把地址/原值填进「改」那一行，
  回车或点「写入」下发，写完自动回读对账。
  「内存跟随 PC」勾上时，停下就自动跳到 `PC & ~0xF`。
  hexdump 一行几个字节**按面板宽度自适应**（<560px 时一行 8 个，否则 16 个），窄面板里不会横向溢出。
* **符号列表**（**变量 tab** 上半）：载入 ELF 后列符号 —— **带类型的全局/静态变量排在最前**，
  然后函数，最后是没有类型的数据对象；上面那个输入框按子串过滤（最多渲染 300 行，超了会提示缩小范围）。
  **点名字** = 把 `p <名字>` 填进命令行；**点 ＋** = 加进监视窗口。
  🚨 **与下半的监视窗口各占一半高度**（用户 2026-10 要求）：两个列表都是 `flex:1 1 0`（**basis 必须是 0**）
  —— 写成 `1 1 auto` 时 flex-basis 取内容高度，符号列表上百行、监视窗口两三行，
  剩余空间就按内容比分配，监视窗口会被压成一条缝。两边的 `min-height` 也必须是同一个值。
  回归：`dbg-page.test.mjs` §10 末（量两个列表的 `getBoundingClientRect().height`，比值要 ≥0.75）。
* **监视窗口**（**变量 tab** 下半）：`w <变量>` / 符号列表的 ＋ / 那个输入框都能加；`wl` 列出、`wd <编号|名字|all>` 删。
  取值时机 = **目标停下来时自动读一遍**（暂停 / 命中 / 单步后都会刷），
  勾上「运行中也刷新」则运行中约 4 次/秒从 RAM 直读（值可能读到写一半的，且占用 SWD）。
  表达式支持 `变量名` / `符号+偏移`（按 u32 读）/ `0x20000000`；**不支持** `a[3]`、`s.member`（见 §8）。
* **SVD 外设寄存器**：内置 STM32F103 / H743 / H750，也可载入自己的 `.svd`。选择外设与寄存器后可手动读取；勾选“运行中也刷新”时，当前 SVD 面板可见期间约每 500 ms 读取该寄存器，不扫描整个外设。变化的值及位域为橙色，约 2 秒未变化后恢复。自动读取让位给调试操作；读取失败会停止运行中刷新并显示原因。
  暂停、命中断点或单步后，当前寄存器会自动读取，与上次暂停时的快照比较；同一次暂停反复读取不会立即抹掉高亮，下一次暂停没有变化则恢复。第一次暂停读取用于建立基线。模型、目标连接变化时清除历史，避免跨芯片比较。标记有读取副作用或只写的寄存器不自动读取；STM32 SVD 不用于 RISC-V 目标。仍应选择与目标匹配的 SVD，缺失的读取副作用标记无法由工具自动推断。
* **源码视图**（左上那块）：停下来（暂停/命中/单步）时按 PC 查行号表，显示 `文件:行` 与上下文，
  当前行高亮、已下断点的行号标红；**点行号 = 在这行下/删硬件断点**（行号表里没有地址的行会明说。
  例如空行、声明、被优化掉的行）。
  看得到**代码文本**需要先点「选择源码目录…」授权一次工程目录（见 §7.1）。
* 命令行（左下那块，xshell 手感）：`h` 看全部命令；**Tab 补全**（命令名 / 符号 / 寄存器 / 断点号 / 源文件名，
  多个候选时先补公共前缀、再按一次 Tab 列出候选）；`↑↓` 翻历史；`Ctrl+C` 中断当前命令、
  `Ctrl+L` 清屏、`Ctrl+A/E/U/K/W` 行编辑；**粘贴多行会排队逐条执行**；
  点输出区（没在选文字时）把焦点还给输入行。常用命令：
  `r` / `r r0 0x1234` / `md 0x20000000 64` / `mw 0x20000000 01 02` / `p g_var` / `w g_var` /
  `b main` / `bl` / `bd 1` / `c` / `s` / `reset run` / `sl` / `src main.c:120` / `info` / `sym RTT`。
  认不出的命令**报错**（不静默），解析失败绝不猜（比如 `md 0x2000 abc`）。
  > `Ctrl+C` 只能"跑到下一步就停"：浏览器没法取消**正在飞的 USB 传输**，
  > 所以按下去之后当前那一笔写完才生效（cmd.js 里每个操作前后都有 `checkCancel`）。
* 侧栏「断点」列表点 `×` 直接删；「RTT」（**RTT tab**）那一栏会**显示 ELF 里 `_SEGGER_RTT` 的地址**
  （地址格留空就用它；手填了就以手填为准），另外也会尝试 `SEGGER_RTT` / `g_rtt` 等别名。

### 7.1 「停下来显示当前源码行」是怎么工作的

1. **行号表**：`app/elf/lines.js` 解析 `.debug_line`（DWARF 2~5 都认，v5 的目录/文件表是
   "格式描述 + 值"两段式），把每个 CU 的行号程序跑成**地址区间**，于是 `at(pc)` 能给出 `文件:行`。
   载入 ELF 时会顺带解析（`SymTab.lines`），失败**不算致命**：符号/变量/断点照常用，只是没有源码行。
2. **源码文本**：浏览器读不到你磁盘上的 `.c`，必须由用户授权一次：
   * Chromium 系点「选择源码目录…」→ `showDirectoryPicker()`（`http://127.0.0.1` 与 https 下可用），
     句柄留着，之后按需读文件；
   * 老浏览器/不想授权就用旁边隐藏的 `<input webkitdirectory>` 那条路（选文件夹 → File 快照）。
   ELF 里记的是**编译机上的绝对路径**（可能是同事机器的 `E:/proj/...`），所以 `source.js` 的
   `resolve()` 从**最长后缀**开始逐级匹配，再退到"同名文件唯一就认它"；匹配不上就老实说"没找到"。
3. **伪源码**（`mock.js` 里）：假目标有寄存器/内存，若喂同一个真 ELF 也能按 PC 显示行号 —— CDP 自测
   就是这么覆盖这条链的（塞一个假的"文件仓"给视图，验证取到文本之后的渲染/高亮/断点标记）。

## 8. 2026-10 新增：按行下断点 / 源码级单步 / 结构体树

这三块都是"MDK/Ozone 的日常动作"，实现上共用一条原则：**能用行号表算出来的，就不去猜机器码**。

### 8.1 按 `文件:行` 下断点（`b main.c:192` / `b main:192` / `b +5`）

* 解析全在 `SymTab.breakSpec()`（纯逻辑，Node 自测）：`文件:行` 先按**文件后缀**匹配
  （`main.c` 能匹配 `/proj/src/main.c`），匹配不到再把 `<名字>` 当**函数**（用它所在文件 + 绝对行号）；
  `+N`/`-N` 是相对**当前 PC 所在行**（需要先停下来，否则明确报错）。
* 反查用 `LineTable.resolveLine()`：同一行取**最小地址**、`is_stmt` 优先（与 gdb 同款挑法）。
* 断点的出处（`main.c:192`）记在 `session.bpNotes`（**不参与 FPB 编码**，纯显示），
  `bl` 与侧栏断点列表都显示它；`bd main.c:192` 也能按同一套解析删。
* 反查不到（空行/声明/被优化掉）→ **报错并说清是哪一种**，绝不"下在附近某个地址"。

### 8.2 源码级单步（`n`/F10 跳过 · `si`/F11 进入 · `fin`/Shift+F11 跳出）

统一底座是 `session._tempBpRun(target, {clearAt})`：**放一个临时比较器 → 运行 → 等它停 → 收干净**。
三条纪律（都写进代码注释了）：

1. **当前 PC 上原本有用户断点时必须先临时摘掉**（否则一放开就原地再命中，看着像"没反应"）——
   由 `_withBpCleared()` 完成；临时断点加在"摘掉之后"的状态里，收尾顺序反过来。
2. **临时断点正好落在用户断点上时不许删**（那是用户的断点）——这种情况干脆不加比较器，直接跑。
3. **FPB 比较器被用户断点占满**时给人话错误（"先删掉一个用户断点"），并把这条提示也放进 `bl` 的输出。

各自怎么算落点：

| 命令 | 落点 | 说明 |
|---|---|---|
| `n` / F10 | `LineTable.nextStmtAddr(pc)`：当前行之后的**第一条 `is_stmt`** | 函数调用整行跳过；遇到**序列末尾**（`seqEnd`，即函数最后一行）会明确拒绝，而不是跑到隔壁函数去 |
| `si` / F11 | 若 PC 处是 `BL/BLX(imm)` → 被调函数的第一条语句（**`prologue_end` 优先**，gdb 同款"跳过序言"）；否则等同 `n`；不是静态可解的调用（`BLX <reg>` 等）→ 退化成**指令级**单步并把原因写进日志 | 目标地址用 `app/dbg/thumb.js` 解码，编解码互验（Node 自测里有往返用例） |
| `fin` / Shift+F11 | **LR 里的返回地址** | 只对最内层栈帧有效（MDK/Ozone 同样如此）；`LR` 是 `0xFFFFFFFx`（EXC_RETURN，核在异常里）或 0 → **明确拒绝**并说明原因，绝不瞎跳 |
| 源码行双击 / `rc <文件:行>` | 该行的 `is_stmt` 地址 | 已在目标地址上时直接回"已经停在这一行上" |

⚠️ **与浏览器的按键冲突（诚实说明）**：`F11` 在 Chrome/Edge 里是**全屏**，页面拦不住；
`F5`（刷新）更危险 —— 按下去会**丢掉整个调试会话**，所以**不绑 F5**。工具栏上那三个按钮与
命令行 `n`/`si`/`fin` 是等价入口，快捷键只是补充。

⚠️ **"下一行"是"地址序的下一条语句"**，不是"源码行号 +1"：对 `for`/`while` 回跳、
一行多语句（`?:`、逗号表达式）这类情况，落点与 MDK 的"+1 行"可能差一条语句（MDK 同样受
行号表精度限制）。要精确跨过某一行就用 `rc <文件:行>` 明确指定。

### 8.3 结构体/数组树（监视窗口 ▸ 展开、`p <结构体>`、位域）

* 类型树来自 `app/elf/dwarf.js` 的 `Dwarf.type(refOff)`：结构体/联合/数组/指针/标量**递归**，
  成员带 `offset`、位域带 `bitSize` + **`bitOffset`（从结构体首字节起算**，DWARF ≥4 用
  `data_bit_offset`，DWARF ≤3 用小端换算 `容器位数 - bit_offset - bit_size`）。
* **一次读整块**（上限 `TREE_LIMITS.maxBytes = 512`），树在本地按偏移解 ——
  展开时不再多读内存（否则一个 20 成员的结构体就是 20 次 SWD 往返）。
* 显示上限（`app/dbg/watch.js` 的 `TREE_LIMITS`）：嵌套 4 层 / 一次 96 行 / 数组显示 16 项，
  超了会写"还有 N 项""只显示前 N 行"这种**明说的截断**，不静默丢数据。
* `u8/i8` 数组可打印时额外给一行 `(字符串)`；越界/读不到的成员显示"（越界 / 读不到）"，
  **绝不拿 0 充数**。
* 展开状态随监视列表一起存 `localStorage`（刷新页面不会把展开的树收起来）。

## 9. 2026-10 发布前压力测试（H743 靶子 + gdb 对照）—— **7 个真机缺陷与修法**

靶子：`tools/target-firmware/stm32h743_dbgstress`（11 段流水线、6 层嵌套、递归/互递归、
函数指针、复杂结构体/位域/联合体/链表）。压测：`node tools/selftest/dbg-hw-stress.mjs`
（真机 81 项；DWARF 5 版 76 项）。对照：`tmp/dbg-gdb-oracle.mjs`（OpenOCD 0.12 + gdb 10.2，
同一颗 akaLinkPro、同一份 ELF）。

压测**抓到并修掉**的 7 件事（每一条都有真机现场）：

### 9.1 位域解码：嵌套结构体里的位域全读错（**最严重**）
`treeRows()` 直接把 DWARF 的 `bitOffset` 当**缓冲区**偏移用，等于假定"位域所在的结构体就在根对象开头"。
位域一旦嵌套（`g_model.flags.bits.level`），解出来的就是根对象头 4 字节的位 ——
实测把 `g_model.magic`（`'MODE'`）的位当成位域值显示。
→ 修法：`readBits(buf, 所在结构体字节偏移 × 8 + mem.bitOffset, bits)`，并按声明类型做**符号扩展**
（`signExtend`，`int32_t bias : 6` 要能解出负数）。
靶子里的"影子字"（`flags.word`）与 gdb 的逐字段核对双双确认修复正确。
自测：`dbg-core.test.mjs` §19（手搭类型树 + 手算字节，不依赖硬件）。

### 9.2 `p`/`w` 不认复合路径（`a.b[2].c`）
DWARF 里只有**顶层**变量，`p g_model.flags` 走"精确查名字"必然查不到，而这是 gdb/Ozone 里最自然的写法。
→ 修法：`symbols.js` 新增 `parsePath()` + `walkPath()`，`typeOf()` 支持 成员/下标 交替的路径
（按 DWARF 成员偏移与数组元素大小累加地址，带**原因**失败：`下标 [9] 越界（数组只有 4 项）`）。
顺带修了两个连带问题：**位域成员要按位取**（早先打出来的是整个 u32）、
**路径走不通时必须作废**（早先 `p g_model.nope` 会拿 `g_model` 的类型画一棵看着正常的树）。
自测：§20。

### 9.3 `fin`（单步跳出）在**非叶子函数**里原地打转
LR 只在叶子函数里才是返回地址；本函数内部只要调用过别人，LR 就被覆盖成"那次调用之后的那条指令"。
实测：H743 六层嵌套里在 `engine_deep_l4` 按跳出，`LR=0x80002bd` 正是本函数里 `bl deep_l5` 的下一条，
连点 5 次纹丝不动（MDK/gdb 会正常跳回调用者）。
更阴的是"陈旧 LR"：函数末尾若是 `pop {r7, pc}`（不含 lr），LR **不会被恢复**，
于是它的值落在**被调函数**里 —— 只看"LR 在不在当前函数里"会跳到**已经返回过的旧位置**。
→ 修法（`session.stepOut`）：
* **快路径**：LR 通过静态校验才用 —— 返回地址**前面那条指令必须是一个"调用当前所在函数"的调用**
  （`bl F` 的下一条才叫"F 的返回地址"）；校验不了就不猜。
* **慢路径**：一条条单步走完本函数，看 **SP 有没有弹回**判断这一帧结不结束；
  途中进了别的函数（调用/中断）就用 LR 临时比较器跨过去，不跟着钻。代价只有"本函数剩余指令数"。
自测：§17b（假目标加了真的 `PUSH`/`POP` 栈语义，否则这条路径根本测不到）。

### 9.4 断点单步遇到分支/返回指令会"跑到随机位置"
这颗探针/内核**不执行 C_STEP**（DHCSR 写入 `0x3000f`、S_HALT 恒定不掉、PC 纹丝不动 ——
F103ZE 与 H743 都是），指令级单步只能靠"在下一条指令上放临时比较器"。
而兜底只放 `pc+len`：`bx lr` / `pop {pc}` / `b` 一跳走，那个比较器永远不会命中 →
白等 2 秒再把核停在一个随机位置（3.3 的"爬栈打转"就是这么来的）。
→ 修法：`thumb.js` 新增 `nextAddrsOf()`（**算落点**：`bx lr`/`bx Rn`/`blx Rn`/`pop {pc}`/`ldr pc`/
`mov|add pc`/`b`/`bcc`/`cbz`/`bl`），**条件分支两个候选都放比较器**，算不出来就如实标"不确定"。
顺带把 `_cStepWorks` 做成**粘性记忆**：失败一次之后不再每步白等 400 ms（单步从 ~500 ms/步 → ~15 ms/步）。
自测：§22（十几条真实机器码逐条钉）。

### 9.5 「复位并停」没停在复位向量上
只写 `C_HALT` 再 `SYSRESETREQ` 是不够的：实测复位后内核照样跑，等我们去"停"它时已经到 `main+0x6c`；
若此刻挂着断点，会**一路跑到断点**（"复位重跑"变成"复位后停在某个断点"）。
→ 修法：复位前置 **`DEMCR.VC_CORERESET`**（内核复位向量捕获，OpenOCD/MDK 的 `reset halt` 同款），
复位后清掉。实测 3 轮都精确停在 `Reset_Handler`（`0x08000880`），且断点在复位后仍然有效。

### 9.6 一次总线 FAULT 会把整条 SWD 链路打死
hexdump 里手输一个不存在的地址（例：H7 的 DTCM 末尾外 `0x20020000`）就会 FAULT，之后连
"读寄存器""读 flash"都一路 FAULT；`abort()`（清 sticky）和写 DP `CTRL/STAT` **都救不回来**，
只有重新走一遍 `_targetInit()` 才恢复 —— 用户看到的是"探针突然瞎了，只能拔插"。
→ 修法：`dap-webusb` 的 FAULT 现场**只标脏**（当次操作如实失败），**下一次访问前**自动
`_healIfFaulted()`（锁外做，避免自锁死）；`session.memRead/memWrite` 把错误翻译成人话
（"目标回了**总线 FAULT** …调试链路会自己重新初始化，不用重连"）。实测 FAULT 之后紧接着读寄存器、
读 flash、单步、下断点、继续 —— 全部正常。

### 9.7 函数最后一条语句要按两次 F10 才跳出
编译器会给"右花括号/收尾"挂**非语句**记录（`is_stmt=0`，实测 `engine_linear` 的
`0x800020c/0x8000212` 都是 `L42` 且非语句）。照停不误会停在 `}` 那一行，看着像"没反应"。
→ 修法：`nextStmtAddr()` 多返回一个 **`tail`**（这条之后同一序列里再没有 `is_stmt` 了），
`stepOver()` 见到 `tail && !isStmt` 就改走"跳出"—— 与 gdb 的 `next` 行为一致。

## 10. 已知边界

| 不做 | 原因 |
|---|---|
| 反汇编 | Thumb-2 解码表几千行 / RISC-V 另一套，与"零依赖"冲突；用 `sym` + 符号落点代替 |
| 局部变量 / 表达式求值 | 要 DWARF 表达式求值（寄存器里、栈上偏移），无底洞；只支持全局/静态变量 |
| 调用栈（backtrace） | 最内层能靠 LR/异常帧做（`fin` 就是），**任意深度**要么要求 `-fno-omit-frame-pointer`、要么解析 DWARF CFI（另一套状态机），v1 不做 |
| 软件断点 | flash 上要擦一页再写回；RAM 上会破坏"同一份固件两种跑法"。**代价**：源码级单步要临时占一个 FPB 比较器，占满时报错而不是降级 |
| `0x20000000` 以上的断点（rev1 FPB） | 硬件比较器只有 27 位地址，`0x9…` 的 QSPI 代码打不了 |
| 监视里的指针跟踪（`*p`） | 只显示指针值本身，不跟进目标（`p *0x24000060` 可以直接看那个地址，但不跟随结构体） |
| 行号表里的**内联函数** | `at()` 只做"地址 → 行"，不做 `DW_TAG_inlined_subroutine` 展开；`b <内联函数名>` 会明确报"认不出" |
| 单步跨过内联收尾的落点 | 与 gdb 口径不同（见 §9 末尾）：gdb 按"行号变化"停，我们按"地址序下一条语句" |
| `fin` 走慢路径时的开销 | 本函数剩余指令逐条单步（上限 400 条）；正常函数几毫秒，函数很大时会有可感知的等待（日志会说明走了多少条） |
| 桥 + OpenOCD/J-Link 的 GDB RSP 兜底 | 计划中（覆盖 OpenOCD 支持的全部芯片，断点免费） |

## 11. 2026-10：RISC-V / JTAG 后端（HPM6800EVK 靶子 + gdb 对照）

同一页、同一套界面，多了一个后端：**`#d-backend` = 「WebUSB · RISC-V/JTAG（HPM 等）」**。
它跟 ARM 那条路复用**全部**上层（ELF/DWARF、行号表、`文件:行` 断点、源码级单步、结构体树、
监视窗口、命令行），只换"跟硬件打交道的那一层"：`app/dbg/riscv.js`（会话）+
`app/dbg/rv.js`（RV32 指令解码，与 `thumb.js` 同形）。

差异都在硬件语义上，记在这里备查：

| 动作 | ARM（SWD/FPB） | RISC-V（JTAG/触发器） |
|---|---|---|
| 断点 | FPB 比较器（rev1 ≤ `0x20000000`；rev2 不限） | **触发器** `tselect/tdata1/tdata2`（mcontrol，8 个）；地址不限 |
| 单步 | `DHCSR.C_STEP`（本机这颗探针不执行 → 兜底"断点单步"） | **`dcsr.step`** 硬件真单步（要临时摘掉起点上的触发器） |
| 停/跑 | `DHCSR` + `AIRCR` 软复位 | `dmcontrol.haltreq/resumereq` + `ndmreset` |
| 读内存 | AHB-AP（任意地址） | SBA（**flash/XIP 窗口除外**，见下） |
| 寄存器 | DCRSR/DCRDR | 抽象命令（**要求 hart 停住**，否则 `cmderr=4`） |

### 11.1 压测抓出来的 8 个真缺陷（都已修，回归钉在自测里）

`s` 的编号与 `tools/target-firmware/hpm6800evk_dbgstress/README.md` 那张表一致。

1. **`_bpAt()` 的地址掩码是有符号的** —— `(addr >>> 0) & 0xfffffffe` 得到**负的** int32，
   而比较的另一边是无符号的 `>>> 0` 结果，于是 **`0x8000_0000` 以上的地址永远匹配不上**。
   后果不是小毛病：`_withBpCleared()` 以为"这个地址上没有断点"，
   **不摘触发器** → 单步原地不动；`cont()` 不先跨过断点 → 一放就跑回同一个断点
   （现场表现："4 个断点只有 1 个会命中"、"点了单步没反应"）。
   ARM 上只要代码放在 `0x9000_0000`（外部 XIP flash）会踩同一个坑。
   → 统一走 `fmt.js` 的 `align2()`。
2. **`si` 会去读"ARM 的 AHB-AP"**：共享代码里 `_readHalfword()` 直接用了 `this.probe.readMem`，
   而 RISC-V 后端上 `this.probe` 是**同一颗探针的 JTAG 实例**，链路上根本没有 AP → FAULT
   （现场报 `SWD FAULT（传输 0/1 条，地址 0x4）`），异常被吞掉后"就当没读到"→ 退化成指令级单步。
   → 改走 `_codeBytes()`（后端自己的读 + ELF 兜底）。
3. **`resumereq` 之后 DM 会"慢半拍"**：写下去的一小段时间里 `dmstatus` 仍报 halted。
   谁在这窗口里读一次状态，就会得到**陈旧读数**——单步表现为"按了没反应"，
   继续表现为"一放就跑回原地"（因为我们在核还没动时就把触发器装回去、把 `dcsr.step` 清掉了）。
   → 新增 `_waitResumed(pc0)`：**先确认真的跑起来了**（running 位 / 不报 halted / PC 变了），再等它停。
4. **`reset halt` 之后断点全失效**：触发器是 **hart 自己的 CSR，hart 一复位就没了**，
   而页面上的断点表还留着 → 界面"看起来有断点"，硬件里一个都没有。
   → `resetHalt()/resetRun()` 之后**重新下发**（`resetRun` 要在"按住复位"时下发，放开就跑）。
5. **`c.jal` 认不出来**：`callEndingAt()` 的判据写成了**整字相等**（`hw === 0x2001`），
   而 C.JAL 除了固定位还带 11 位立即数 —— 于是**只有"跳到偏移 0"才认得出**。
   现场 `engine_deep_l4` 用 `c.jal` 调 `deep_l5`，`fin` 因此判定"ra 不是本帧返回地址"，
   改走"一步步走完本函数"的慢路径（400 条还没走出去）。
   → 判据改掩码 `(hw & 0xe003) === 0x2001`。
6. **flash（XIP）窗口不能走 SBA**：`0x8000_0000` 段用 SBA 读会**超时 5.3 s，并把 DM 打乱**
   （事后 `dmstatus` 读回 `0x67adb267`，version=7 的垃圾；USB 还得复位端口）。
   而代码与 `const` 都住在那儿。
   → 该窗口直接用**载入的 ELF 里的只读段**（`.text`/`.rodata`；可写段不兜底），
   并在命令行里**写明**"这份值来自 ELF，不是从目标实时读回来的"。指令取指同样优先用 ELF。
7. **`dm.init()`（DM 复位）会把核放开跑** —— 调试会话里"原来停着"的话，
   重新初始化之后必须再停一次，否则后续抽象命令全是 `cmderr=4`。
   → `memRead()` 的"复位 DM 重试"路径里已处理。
8. **偶发连不上探针**（`响应回显 0x3 ≠ 命令 0x0`）：上一个会话在 IN 端点里留下的陈旧响应包。
   → `connect()` 里"关句柄 → 等一下 → 重开"，最多 3 次。

### 11.2 与 riscv gdb 的对照结果（同 ELF、同探针、同一颗核）

生成基线：`node tmp/probe-free.mjs --blank && node tmp/rv-gdb-oracle.mjs`
（OpenOCD 0.12 + `hpm_sdk/boards/openocd` 的 `probes/cmsis_dap.cfg` + `soc/hpm6880.cfg`
+ `riscv32-unknown-elf-gdb`；**不要** source 板级 cfg，它要 HPM 定制的 hpm_xpi 烧录驱动）。

| 比什么 | 结果 |
|---|---|
| `engine_linear` 内**指令级**单步 19 步落点（我们 `s` ↔ gdb `stepi`） | **逐地址完全一致** |
| `b engine.c:22` / `b model.c:123` 落点 | 与 gdb 的**行号表地址**一致（`0x8000578c` / `0x80006094`） |
| 位域排布（word/spare/bias… 逐字段） | gdb 独立核对 = 页面假设 |
| 靶子 trap 计数 `g_trap_count` | 0（整轮压测没有触发任何异常） |

两条**口径说明**（不是缺陷）：

* gdb 的 `break 文件:行` 会**跳过函数序言**落到第一条语句上（`engine.c:22` → `0x80005794`），
  页面按用户点的那一行 / DWARF 行号表的记录地址（→ `0x8000578c`）。对照取后者，
  前者的值在 oracle 的 `bpAddrPrologue` 里另存着。
* gdb 的 `next` 在这块板上会**卡在第 29 行那个调用上**：跳过调用需要在返回地址插临时断点，
  而代码在 flash 里、软件断点写不进去。所以基线用 `stepi`（指令级），两边都干净。
