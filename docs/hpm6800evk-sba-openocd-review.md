# HPM6800EVK：Web SBA 与 OpenOCD 对照审查

日期：2026-10-07。范围：浏览器内 WebUSB → CMSIS-DAP JTAG → DMI → SBA；调试、RTT、烧录共用的内存通路。

用户确认后已完成共用 DMI/SBA 实现修正与离线回归，保持 Web 零安装架构。下面的差异和缺陷复现记录来自修改前版本，文末列出修正结果与尚未完成的真机验收。

## 结论

用户转述的六条建议方向正确，但还漏了一项更基础的问题：Web 的 DMI BUSY 常量写错了。当前问题不能统一解释为 HPM6800EVK 的特殊性，也不能通过反复复位目标来证明 SBA 算法正确。

修改前可以直接证明的是：状态码错误、尾字多读、清错时违反忙状态约束、错误复验不完整、写入完成判定过早，以及普通变量读取会隐式系统复位。本次实现和回归覆盖了这些问题。

修正这些问题后，板级总线挂起、缓存一致性和特殊地址窗口仍须分别用真机验证。本报告没有断言这些硬件问题不存在。

## OpenOCD 中值得参考的流程

| 层次 | 行为 | 本地参考位置 |
|---|---|---|
| DMI | 分别核对发请求和收结果时的响应；BUSY 时清 DTM 粘滞状态、增加空转延迟、有界等待 | `riscv-013.c:456`、`:563` |
| SBA 空闲 | 轮询 `sbbusy`，超时返回失败 | `riscv-013.c:2545` |
| 块读 | 启动首读；单字不启用 `sbreadondata`；多字读取留下尾字，空闲后关闭续读，再取尾字 | `riscv-013.c:2682` |
| 冲突恢复 | 区分 DMI BUSY、SBA busyerror 和真实总线错误；清错、增加对应延迟、核对硬件地址进度 | `riscv-013.c:2792`；当前上游 `read_memory_bus_v1` |
| 块写 | 批后等待系统总线完成，根据错误和硬件地址决定后续操作 | `riscv-013.c:3654`、`:3726` |

当前上游读路径在 busyerror 恢复时还明确关闭自动读触发，并处理最后已经完成的值。恢复不能只凭软件批次索引猜测总线进度。所检查的这些 SBA 函数没有用 `ndmreset` 作为内存读失败的自动恢复。

注意：OpenOCD 的加速路径也会乐观地依靠延迟，随后检查并恢复冲突；它不是每个字都先轮询空闲。Web 的第一阶段应先建立保守、可验证的基线，再移植加速思想。

## 修改前 Web 中已经确认的差异

本节代码行号对应审查时版本，修正后已发生变化。

### 1. DMI 状态码错误，恢复与上游有差异

位置：`app/flash/hpm/jtag.js:175`；`app/flash/hpm/riscv-dm.js:262`、`:289`。

`DMI_STATUS.BUSY` 被定义成 1；响应 3 被注释成“不属于 BUSY 的错误态”。实际上响应 3 就是 BUSY。探针固件 `firmware/application_5301/src/riscv/riscv_jtag.c:18-20` 本身也定义 SUCCESS=0、FAILED=2、BUSY=3，所以目前没有依据把 Web 的差异解释为板级协议。

Web 读写都丢弃发请求那次扫描的响应，只判断后续 NOP；OpenOCD 检查两阶段。规范的 BUSY 状态具有粘滞性，后续 NOP 通常也会暴露它，所以“丢弃首阶段响应”本身还不能作为独立的数据错误证据。修改时需采用符合粘滞语义的模型验证请求接收、恢复和完成进度，尤其避免批量路径误计已完成请求。

响应 3 的处理虽碰巧调用了 dmireset，但没有增加 DMI 延迟。响应 2 的粘滞失败也没有形成明确清理流程。读循环的时间检查没有覆盖响应 3 分支，写路径没有可传递的时间预算。

### 2. 单字与块读尾字都会多发总线访问

位置：`app/flash/hpm/riscv-dm.js:881-955`。

块读始终使用包含 `sbreadondata` 的配置，直到读完所有字都没有关闭它。读 N 个字会启动 N+1 次总线读取；即使只读一个字也存在同样问题。

这会访问请求范围以外的地址。最后一个合法字之后若是未映射窗口，会把一次合法请求变成总线错误；若是外设，也可能产生额外读取副作用。现有完整请求范围检查并未覆盖这个额外预取。

### 3. 等不到空闲后仍然写 SBCS 清错

位置：`app/flash/hpm/riscv-dm.js:588-621`。

`sbaClearErrors()` 最多轮询 25 次，循环耗尽后仍继续读取并写 `sbcs`。规范要求 `sbbusy=1` 时禁止写 `sbcs`，这种写入行为未定义。函数还吞掉部分 DMI 读取失败，可能让上层误以为清错成功。

`sbaConfig()` 的配置缓存也不能替代实时空闲和错误检查。正常返回后仍有尾字预取在飞，下一次配置或地址访问可能撞上它。

### 4. 等待忙状态结束时没有重新判错

位置：`app/flash/hpm/riscv-dm.js:813-835`。

`_checkSbcsAt()` 只对第一次 `sbcs` 判断错误。如果首次是 BUSY，下一次 BUSY 落下同时出现 `sberror`，函数直接返回成功。真实错误可能正是在事务结束时出现。

### 5. 批尾 SBCS 的 DMI 状态未验证

位置：`app/flash/hpm/riscv-dm.js:319-335`、`:768-785`。

读写批处理只取尾部响应的 `.data`，未检查这笔 `READ SBCS` 的 `.op`。当尾部响应 BUSY/FAILED 时数据不能作为成功证据；如果数据恰好是零，整批就可能被接受。

### 6. 重试把不同错误混在一起，并丢失配置

位置：`app/flash/hpm/riscv-dm.js:845-862`、`:917-942`、`:987-1000`。

`readMem()` 按错误消息包含 `sbcs/sbbusy` 来决定重试，所以真实 `sberror` 也可能被重复访问。应使用结构化状态和阶段信息，而不是错误文案。

批量失败清错后，`_sbcsCfg` 被置空，但读写降级路径直接重写地址，并未明确重新建立需要的 SBA 配置。当前清错写入保留旧自动触发位，暂时掩盖了这项依赖；采用正确的停止触发清错流程后，必须一起修正。

读写整批重做也不能不加区别地用于有副作用的地址。需要核对硬件 `sbaddress`、可确认的完成进度和访问用途；不明确时返回失败。

### 7. 写入仍在忙时返回成功

位置：`app/flash/hpm/riscv-dm.js:1005-1012`。

`writeMem()` 收尾只判断错误位，未等待 `sbbusy` 清零。DMI 已接收 `SBDATA0` 写入不等于系统总线写入已完成。下一笔访问可能因此撞忙，或者上层提前开始运行尚未完全写入的代码。

### 8. 普通变量读会进入系统复位阶梯

位置：`app/dbg/riscv.js:362-378`、`:472-487`；`app/rtt/riscv-mem.js:76-95`。

调试会话只凭 `lastSbcs` 带 busyerror 就进入 `_repairStuckSba()`；该函数不是单纯清错，而是重新初始化 DM，并反复写 `ndmreset`。busyerror 表示发生过访问冲突，本身不是“硬件不可恢复”的判据。

RTT 读取失败也会自动调用 `dm.init()`。普通读取应保持程序现场；不能把复位、重设断点和重新读取包装成透明恢复。需要复位时，交给明确的用户操作。

## 修改前的验证和测试缺口

现有 `dbg-riscv-memory.test.mjs` 全部通过；`hpm-flash.test.mjs` 为 94 通过、0 失败。与此同时，针对当前生产方法的独立离线检查得到以下结果：

| 场景 | 修改前结果 | 正确要求 |
|---|---|---|
| 模拟 RAM 的最后 4 字节，地址 `0xfffc` | 读失败，`sbcs=0x15f000`；多预取进入未映射区 | 只访问合法最后一个字并成功 |
| 数据响应成功，批尾 `READ SBCS` 响应 BUSY=3、数据为零 | `sbaReadBurst(2)` 返回 `ok=true` | 拒绝使用无效状态数据 |
| 检查序列从 BUSY 变为 SBERROR | `_checkSbcsAt()` 返回成功，`lastSbcs=0x7000` | 报告事务完成时出现的错误 |
| 始终 BUSY 且 busyerror 置位 | `sbaClearErrors()` 仍写 SBCS 两次 | 超时退出，禁止忙时写配置 |
| 单字写收尾一直 BUSY | `writeMem()` 返回成功，`lastSbcs=0x200000` | 等待完成或超时失败 |

除了 RAM 边界例使用现有模拟 TAP/DTM，其他例子在生产方法的注入接口模拟状态响应。这些是软件行为复现，不是 HPM6800EVK 真机测量。另一个探索性注入令请求阶段 BUSY 后直接出现成功，因不符合规范的粘滞 BUSY 语义，已排除出缺陷证据。

测试缺口也已确认：`hpm-sim.mjs` 的 SBA 是同步完成；没有真实忙窗口和异步完成错误。`burstRig` 桩绕过配置，把数据读取简化成即时地址推进。测试还通过 `_repairStuckSba` 空桩认可自动恢复，不能证明恢复过程中没有系统复位。

## 用户确认的实施顺序

1. **建立独立的异步协议测试基线。** 模拟器以规范常量为判据，加入总线延迟、粘滞 DMI BUSY/FAILED、忙时配置违规、边界地址和可记录的实际总线访问。先让上述缺陷成为能失败的回归用例。
2. **修正共用 DMI/SBA 状态处理。** 核对请求与响应两个阶段；区分 DMI 延迟、SBA 读延迟、SBA 写延迟；统一空闲等待和清错复验；让所有重试、清错和底层调用受共同时间预算约束。发生真实总线错误及时返回，禁止按错误文字无条件重读。
3. **先建立逐字正确路径。** 首读和每笔完成均检查状态；单字关闭续读；多字尾字在空闲后关闭续读再取出；写完成必须等待总线。失败不接受部分不可信数据，不把超时当作事务已取消。
4. **移除普通读取的隐式复位。** 调试变量和 RTT 普通读取只进行允许的协议清理，失败清楚报错。DM 初始化与系统复位继续由明确的连接或复位动作承担。
5. **恢复批量性能。** 借鉴当前上游的独立自适应延迟、完成进度核对和尾字处理；每笔 DMI 响应包括批尾状态均验证。清错后重新配置。保留逐字降级和 512 字节包预算，避免默认永久关闭批量。
6. **HPM6800EVK 真机对照。** 明确记录实际 OpenOCD 版本和配置，使用 `riscv set_mem_access sysbus` 排除方法回退；分别验证 RAM 单字、非对齐块、结构体、批次边界、reset-halt 后读取、运行时 RTT、延迟/冲突后再次读取。比对完整数据和访问范围，并核对变量读取未改变 PC、运行/停机状态及断点。通过正确性验收后记录吞吐量。

预期改动文件：`app/flash/hpm/jtag.js`、`app/flash/hpm/riscv-dm.js`、`app/dbg/riscv.js`、`app/rtt/riscv-mem.js`、相关模拟器和自测文件；更新对应说明文档。

保持浏览器零安装架构。当前 XIP/SBA 限制及 ELF 只读镜像来源标注继续保留，是否开放特殊窗口需另有真机证据。正常产品使用不依赖本机 OpenOCD；OpenOCD 只用于开发对照。

验收标准：上述回归场景通过；不在 BUSY 时写 SBCS；没有请求范围之外的尾字预取；DMI 或总线错误不能伪装成功；失败有界退出且不留下并发重试；普通读取不触发 DM/系统复位；真机逐字与批量结果一致。

## 已实施的修正

- DMI 响应使用独立状态码：SUCCESS=0、FAILED=2、BUSY=3；核对请求和结果阶段，以及批尾 SBCS 的响应。粘滞错误只通过 `dtmcs.dmireset` 清除。BUSY 增加 DMI 空转延迟；结果不确定的读取返回失败，不盲目重发有副作用的访问。
- 配置和清错前等待 `sbbusy=0`。清错只写可写配置及实际置位的 W1C 位，关闭自动读触发，之后再次读取状态确认。超时不写忙中的 SBCS。
- 逐字读取等待实际完成；单字不启用 `sbreadondata`。批量读取把最后一个字留在批次之外，空闲后关闭续读，再取最后的数据。写入等待系统总线实际完成后返回。
- 保留批量访问。DMI、SBA 读、SBA 写各自学习延迟；超过 64 拍的空转按多条序列完整发送。批量容量按实际序列字节数、响应容量和 512 字节包上限计算，空间不足时采用逐字路径。
- SBA busyerror 恢复参考 OpenOCD 的硬件地址进度。读路径保留已完成前缀，在关闭自动读和清错后取出最后的驻留数据；写路径只继续未提交的字。真实 `sberror` 报错，禁止整批无差别重做。
- 内存事务串行执行，等待、重试、恢复和清理共用时间预算。底层传输超时后隔离当前 transport，排队请求和迟到的结果不会触发新的命令；USB OUT/IN 也使用剩余预算。
- 删除调试器普通变量读取的 `_repairStuckSba` 自动复位阶梯，RTT 普通读取不再调用 `dm.init()`。保留明确的连接、重新连接和复位操作；RTT 连接健康检查不升级为系统复位。现有 XIP 读取保护继续保留。

主要实现位于 `app/flash/hpm/riscv-dm.js`，由烧录、调试器和 RTT 共用。新增 `tools/selftest/riscv-sba-async.test.mjs` 已接入默认离线入口；模拟器按 TCK 推进异步事务，记录真正发起的总线访问，能检查重复访问和忙时写配置。

延迟矩阵和访问计数来自模拟器，不是板上吞吐量或物理总线测量。专项最后增加了写 DMI BUSY 的提交进度、真实写错误、逐字/批量写延迟矩阵以及 USB OUT 后预算耗尽的验证。

首次预检根据探针报告的 **0 mV** 没有继续真机测试。用户随后确认板子在线，重新启动 Web 成功读到 TAP `0x1000563D`；此时 HID 电压字段仍为 0 mV，说明该字段不能独立作为目标离线的判据。

随后对用户提供的 `lwip_tcpecho/flash_sdram_xip` ELF 和真实板子完成了复现与修正：`desc=0x4000b600` 位于外部 SDRAM，复位停在 `_start=0x80003000` 时 DDR0 尚未开启。强制 OpenOCD `sysbus` 读取该地址也超时，排除了 `progbuf` 回退造成的误判。启动代码在 `_start+0x16` 调用 `_init_ext_ram`，完成后返回 `_start+0x1a`；SDK 初始化 DDR 后等待 `DDRCTL.STAT.operating_mode=1`。

新增的保护识别 ELF 中 HPM6880 DDR 初始化符号，先读取常开 SYSCTL 的 DDR0 资源时钟状态，时钟稳定后才读取 DDRCTL 状态。初始化前不访问 SDRAM，显示等待提示；继续运行后即时恢复，不加入坏地址冷却、不改写时钟、不隐式复位。新回归也修正预算末尾不足以完成 USB 往返时继续发请求的问题：逻辑 SBA 超时不再误伤可用的 DMI 控制通道，真正的在途传输超时仍保持隔离。
