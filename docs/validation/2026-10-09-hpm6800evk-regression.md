# HPM6800EVK 回归异常与 RTT / JScope 对照分析

测试日期：2026-10-09～10（北京时间）。实机 HPM6800EVK / HPM6880，JTAG ID `0x1000563D`，目标 CPU 600 MHz。用户已授权擦写，不做原固件备份。

## 结论

最初的 RTT Viewer `DMI_INVALID op=1` 由回归脚本触发：脚本误把成功状态文字当作故障，在读操作尚未结束时初始化调试链路，破坏在途事务。修正脚本后可以正常读取。

RTT 转发约 1.385 MiB/s，与历史 1.376～1.377 MiB/s 相当。另发现浏览器接收偶发缺口；序号 + CRC 实测把问题定位到浏览器接收路径，增大 RTT 接收缓冲到 64 KiB 后，包含页面停顿的 60 秒录制通过全文件校验。

JScope 饱和档确有小幅下降。相同网页、目标 ELF 下，旧探针源码重编译得到 304.245 kSa/s，新版修改前 297.203 kSa/s，优化后 301.884 kSa/s，下降由 2.31% 缩小至 0.78%。逐字读取路径仍比旧版低约 1.89%，没有宣称完全恢复。常用非饱和档符合预期。

详细测量、失败记录与时间线见 [结构化证据](2026-10-09-hpm6800-regression-evidence.json)。原始日志、二进制记录及对照构建保存在本地忽略目录 `tmp/hpm-regression-20261009`，未上传。

## DMI 错误原因

原脚本的 `waitFirstPoll` 用 `#r-err.textContent` 是否非空判断故障。但成功识别控制块后，该节点也会显示“控制块 0x1240000，上行缓冲 32768 B”，且 class 为 `ok`。

实机插桩顺序：

| 相对时刻 | 事件 |
| --- | --- |
| 5854.7 ms | 第一次 32,767 B RTT 读取开始，active=1 |
| 5934.8 ms | 脚本启动 `probe.recover()`，此时读取仍在执行，页面状态为成功 |
| 6309.5 ms | RTT 写回 4 B RdOff，地址 `0x1240028` |
| 6311 ms | 恢复过程同时执行 `dm.init()`，重置 TAP / IR |
| 6312.4 ms | 在途写回返回 `DMI_INVALID op=1` |

同一探针与网页，只去掉脚本的侵入式恢复，首轮读取立即通过，Viewer 约 60 KiB/s，损坏计数 0。这证明该次错误不是端口适配后的 Flash 算法失效。

问题代码来自 `5ba3e27`（2026-10-04），早于本次 HPM porting。它是旧脚本的潜在竞态，不能因为这次才触发，就归因于最近重构。脚本现在只观察真实错误状态，等待正常轮询自行完成；测速按完整轮询边界计数，失败和未完成阶段也会保留到报告中。

### 为什么增加序号和 CRC 测试

原 `hello world!\n` 重复模式，只能发现相位断裂，不能定量判断丢失、重复，更不能测全通道每比特误码率。修改前接收配置的 6 份录制共 88,391,679 B 中，4 份连续，2 份各有一处相位变化。加上最后一轮 64 KiB 接收配置的综合验收记录，7 份共 103,096,319 B，仍只有原先的 2 处断点；最终记录连续。固定相位校验会把断点后的所有正常文字都误算成坏字节；本报告改为记录断点并重新同步。

追加临时固件使用 BLOCK 模式的 32 KiB RTT 环，连续输出 256 B 帧：`RTSQ`（4 B）、小端 uint32 序号（4 B）、244 B 已知载荷、CRC32（4 B）。载荷字节 i 为 `((sequence+i)^0x5a)&255`，i=8～251；CRC32 为 IEEE 反射多项式 `0xedb88320`，覆盖前 252 B，初始与最终异或均 `0xffffffff`。

| 接收路径 / 条件 | 窗口 | 文件字节 | CRC 失败帧 | 缺失序号 | 重复 / 乱序 |
| --- | --- | --- | --- | --- | --- |
| Web Serial，4 KiB，第一次普通录制 | 30 s | 43,581,440 | 2 | 10 | 0 / 0 |
| 原生串口，接收队列 1 MiB | 30 s | 43,646,976 | 0 | 0 | 0 / 0 |
| Web Serial，64 KiB，普通录制 | 30 s | 43,646,976 | 0 | 0 | 0 / 0 |
| Web Serial，4 KiB，普通复测 | 30 s | 43,745,280 | 0 | 0 | 0 / 0 |
| Web Serial，4 KiB，每秒主线程停顿 25 ms | 30 s | 43,827,200 | 5 | 25 | 0 / 0 |
| Web Serial，64 KiB，同样停顿 | 30 s | 43,778,048 | 0 | 0 | 0 / 0 |
| 修改后的默认配置，64 KiB，同样停顿 | 60 s | 87,379,968 | 0 | 0 | 0 / 0 |

最后一项共 341,327 个完整帧通过 CRC 与载荷校验，在线与离线结果一致。53 B 开始碎片和 203 B 结束碎片是录制切在帧中间，不当作损坏或丢失。4 KiB 首次普通录制的缺号率约 58.7 ppm（10 / 170,247）；25 ms 停顿测试约 146 ppm（25 / 171,219）。CRC 失败帧可能是缺字节造成的拼接，不能当成独立比特翻转来计算 BER，缺号计数也已涵盖未通过 CRC 的序号，二者不可相加。

数据缺口在线接收时就存在，导出文件与在线结果一致，因此不是 OPFS 导出过程造出来的。原生接收正常、增加缓冲及受控停顿的 A/B 支持浏览器接收缓冲对宿主停顿的承受能力是关键因素；尚未直接测量 Windows 内核队列或 Chromium 服务内部，不能把每个缺字节唯一定位到某个内部队列。

产品修改仅将 RTT 页发起的会话设为 64 KiB，普通 UART / SPI-CDC 等仍为 4 KiB。保留每 8 ms 让出事件循环的机制，防止旧版曾发生的大缓冲下页面饥饿。本轮物理流量为约 1.385 MiB/s，未接 F103 来重验其 2.9 MiB/s 上限；另有 64 KiB 大块模拟页面测试验证接收、记录和页面响应。

首次临时在线校验器有一个载荷比较优先级错误，造成无意义的 payloadBad 大计数；已修正并重新离线核验原文件。表中全部为正确校验器结果，CRC 与缺号计算未受该错误影响。

### 下降原因与处理

新版主循环增加了 SWO 时钟租约服务等工作。分别测试去掉新增派发、只加 SWO 空闲门控、将函数放入 ILM，以及组合方案。只加门控不能恢复速度，去掉新增派发或改变主循环位置能明显改善饱和性能，说明主循环派发与指令布局是主要影响因素。XIP 指令工作集 / 缓存冲突是与这些干预结果一致的解释，但未记录 cache-miss 硬件计数器，因此是推断。

最终保留两项小范围改动：主循环放进 ILM `.fast`；SWO 无待处理请求且无活跃租约时，用内联状态检查跳过服务调用。状态仍是 ISR 与主循环共用的权威状态，不额外维护可能失步的副本；活跃租约仍持续处理心跳超时与时钟恢复。ILM 约占 32,240 B / 128 KiB。没有改变 RISC-V SBA 算法或提高 CPU 时钟来隐藏开销。

2 µs 饱和档和关闭批读后的剩余差距尚未逐周期定位，不能承诺新功能完全没有成本。默认批读在 3.25 µs 的稳定吞吐已与旧版持平；新增服务、链接布局等因素尚有可能贡献剩余开销。

### 零误码不等于零跳采样

- 8 秒矩阵中自适应模式的 USB 丢包、读错误、契约坏值均为 0；8 变量 @40/47/60 µs 分别为 25.000/21.277/16.667 kSa/s。8 变量 @40 µs 加 25 ms 宿主停顿，自适应模式仍无 USB 丢包。
- 关闭自适应并加停顿会溢出：旧版 USB 丢 3,437，新版修改前 2,805，优化后 3,411（约 1.70%）。这不是默认模式，也不是新增回归。
- 2 µs 请求等于 500 kSa/s，超过实际约 302 kSa/s 能力，优化后跳过请求周期约 39.62%；旧版约 39.15%。3.25 µs 优化后跳采约 1.61%，旧版约 1.70%。这些是探针没有按请求周期产生的样本，不是传输坏值。
- 低速综合验收的单变量 20 µs / 三变量 30 µs：50.000 / 33.333 kSa/s，探针跳拍、USB 丢包与样本缺口均为 0。
- HiTick 校验单变量约 302.395 kSa/s；双字段 @20/25 µs 为 50/40 kSa/s，坏值和传输丢失 0；少量跨字段相位差在既定 5 tick 诊断预算内。多字段读取并非原子快照，不按原子快照误判错误。

## 调试、异常和兼容性检查

优化后探针实际通过 57 项调试压力检查，包括断点、复位、单步 / 跨函数执行、8 槽触发器、结构体 / 位域以及 40 轮变量交互。19 个单步地址与工具链反汇编基准核对通过，未发现触发器泄漏。

另实际烧录非法指令靶子，网页异常现场读取成功：`mcause=2`、`mepc=0x80005554`、`mtval=0xffffffff`，正确显示非法指令，读取 error=null。通用 RISC-V CSR 不包含完整异常保存栈，未声称恢复出异常前完整调用栈。

SWO 服务兼容检查：固定 1 Mbps 租约、心跳、手动释放；23 Mbps 精确匹配实际把 PLL1 调到 920 MHz、UART 根时钟 230 MHz（OSR=10，UART divider=1），租约超时恢复 PLL1 800 MHz 和默认 UART 240 MHz。36 个时钟节点、CPU 时钟与 PLL1 配置前后核对通过。

额外试探任意值 11,234,567 baud 时，原有 SWO 精确匹配代码出现 `rc=-8` 回读校验失败，并需重启恢复 HID。该问题未在此次吞吐修复中解决，另列为待处理项；不能把已通过的 23 Mbps 用来证明所有任意波特率都正常。
