# 网页 SRAM 传输优化（2026-10-16，用户要求"把网页端传输找回来"）

**结论：网页路径已经贴着探针的「包长 1024 B + 每 1 KB 必须重写 TAR」结构极限；能回收的是
产品层的造帧开销——造帧热路径 3.7× 提速（20 KiB 写：0.265 → 0.071 ms），同会话 A/B 里
产品基准写 **+8.8%**（2.688 → 2.924 MB/s）；读方向与原生持平（A/B：产品 2.916 / 裸帧 2.695 /
原生 2.93 MB/s）。再快只能改探针固件。**

## 1. 选型实验（微基准 micro.mjs，20 KiB @0x20000000，60 MHz SWD，48 MHz 靶子）

帧型探测（depth=1 逐帧看原始响应，确认两种帧型都可用）：

| 帧 | 请求 | 响应 |
| --- | --- | --- |
| TAR 写（DAP_Transfer 0x05） | `[5,0,1,5,addr(4)]` | `[5,1,1]` |
| 逐字写 | `[5,0,1+words,5,addr,(13,data)×words]` | `[5,1+words,1]` |
| 逐字读 | `[5,0,1+words,5,addr,15×words]` | `[5,1+words,1,data…]` |
| 块写（DAP_TransferBlock 0x06） | `[6,0,cnt_lo,cnt_hi,13,data…]` | `[6,cnt_lo,cnt_hi,1]` |
| 块读 | `[6,0,cnt_lo,cnt_hi,15]` | `[6,cnt_lo,cnt_hi,1,data…]` |

探针广告：**包长上限 1024 B**（info 0xFF）、**在飞深度 4**（info 0xFE）；实测把深度加到 8/12 无收益。

**1 KB TAR 回绕仍然存在**：链式块（只写一次 TAR、后续块靠自增）写入 20 KiB 后逐字节回读
**第一字节就对不上**（`chainWriteVerified={ok:false,firstDiff:0}`）⇒ 每个 1 KB 页都必须重写 TAR
——与现有实现的做法一致。

裸帧计时（深度 4，3 次均值；chain 仅作反例，数据是错的）：

| 方案 | 读 MB/s | 写 MB/s | 命令数/20 KiB | 出向字节 |
| --- | --- | --- | --- | --- |
| **words（现状：页内嵌 TAR + 203/53 字）** | 2.93~3.00 | **3.01~3.29** | **40** | 25920 |
| block（每页 TAR + 254/2 字块） | 2.56~3.20 | 2.81~3.16 | 60 | 20840 |
| chain（只写一次 TAR） | 3.38~3.43 ✗ | 3.53~3.59 ✗ | 22 | 20593 |

⇒ **现状的 words 帧型就是最优：命令数最少（每页 2 个）优先于字节数。**

结构上限：包长 1024 与「每 KB 一次 TAR」共同决定下限 = **2 个包 / 1 KB**（40 包 / 20 KiB）。
`DAP_ExecuteCommands(0x7F)`（固件已实现：`[0x7F,cnt,cmd…]` → `[0x7F,cnt,resp…]`）能把 TAR 与块
塞进同一个包，但页内仍要第二个包收尾（1008 B + 16 B），**往返数不变**，故未采用。

## 2. 产品层回收：造帧热路径

`benchmarkSram` 只把 `write()/read()` 计时，而造帧发生在里面。原实现用
`req.set([...])` + `new DataView().setUint32()` + 每字 `bytes.subarray()`；实测 20 KiB 一次写
的造帧成本 **0.265 ms**（占一躺 ~6.5 ms 的 4%），直接下标写只要 **0.071 ms**（3.7×）。

改动：`app/flash/sram-transfer.js` 的写帧改成逐字节下标写（读帧本来就只 `fill`，无开销）。

同会话 A/B（`bench-once.mjs`，60 MHz，20 KiB×3 轮，各 4 次）：

| | 读 MB/s | 写 MB/s |
| --- | --- | --- |
| 优化前 | 2.534 | 2.688 |
| 优化后 | 2.513 | **2.924（+8.8%）** |
| 裸帧上限（micro words） | 2.93~3.00 | 3.01~3.29 |

产品读 vs 裸帧读（`read-ab.mjs`，交替 4 对）：**2.916 vs 2.695** ⇒ 产品层读方向已无额外开销。

## 3. 与原生 / akaLinkPro 记录的关系

- 原生 OpenOCD（同靶子、同档位，本日实测）：写 3344 KiB/s = 3.42 MB/s（**墙钟 3101 = 3.18**）、
  读 2931 KiB/s = 3.00 MB/s。
- 网页（优化后、裸帧口径）：写 3.01~3.29、读 2.93~3.00 ⇒ **读持平；写与"墙钟"口径持平**，
  与"OpenOCD 纯传输自计时"口径差的约 5% 属于计时口径与流水起跑，不是可回收的产品开销。
- 24 组产品基准复跑（`production-ui-after.json`，48 MHz 靶子）：**24/24 校验通过**；与优化前那次
  跨会话基线相比在噪声内（±8%），因此增益以**同会话 A/B** 为准（跨会话对比不可靠）。

## 4. 边界与后续

- 想再快只能动探针固件：**放宽包长上限（>1024）** 或 **让 TAR 自增跨 1 KB** —— 两者都能把
  每 KB 的往返从 2 降到 1，理论上接近翻倍（本轮实测链式写 3.57 MB/s 就是"无回绕"时的样子）。
- 本轮不改协议语义、不改帧型、不改任何判据；只回收造帧开销。
