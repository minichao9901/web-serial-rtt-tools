本轮完成已有修改的本地提交、当前代码审计和历史测试数据复核；没有重新烧录设备，
没有进行新的真机测速，也没有修改采样算法。离线数字复算见
[审计结果 JSON](2026-10-07-scope-rate-audit.json)。

已有工作提交：网页 `b844956`；SDK 的 tcpecho 非缓存观察状态修改 `fb2c8ae`。
用户其余工作文件与探针 ELF 未纳入提交；未 push。

## 结论

1. 当前“标定”能测当前后端的单次读取成本，但不是端到端稳定采样率。
   “用建议周期”存在后端、读跨度和标定失效判断上的问题，不能保证无损。
2. 最明确的历史零值跳点出在探针 RISC-V 流水线，已修复：每 32 拍坏一个值。
   多变量之间的撕裂属于目标运行中被依次读取的快照一致性问题。
3. 高频丢拍既可能发生在探针读取/调度，也可能由主机排空不及触发设备缓冲耗尽。
   页面端到端数据尚不能把所有 USB 缓冲损失归因于绘图，更不能把它直接叫成 USB 线速上限。
4. 当前页面“零丢包”只表示没有 seq 缺口。设备没采到的拍不会产生包序号缺口，
   实际严重丢拍的历史会话也被显示成“零丢包”。

JScope 是网页采集/绘图功能；HSS 是探针采样器的单字快速读取及相关性能路径。
二者不是两条独立 USB 数据链路。当前短批次只用于 SWD 单字、周期不超过 3 µs，
每批最多 16 拍；RISC-V/JTAG 和多跨度仍逐拍返回主循环。

## 当前标定和公式的问题

### 标定范围

探针 `scope_run_bench()` 紧循环 2,000 次调用 `scope_sample_bytes()`，使用当前
`s_backend`，包括相应读取和拷贝成本。计时器为 24 MHz，所以网页
`ticks / 24 / iters` 的单位换算正确。

它不包含正式采样时的 deadline 调度、每包流水线收尾、USB 推包、其他主循环服务、
主机接收、入库和绘图；也不验证读值契约。M0 的 `1 / readUs` 只是读取吞吐上界。

源码位置：网页 `app/scope/view.js` 的 `_benchNow()`；探针
`firmware/application_5301/src/scope/scope_sampler.c` 的 `scope_run_bench()`。

### 已复算的问题

| 问题 | 当前行为与后果 |
| --- | --- |
| RISC-V 标定自相矛盾 | `_benchNow()` 正确请求 RISC-V；`updatePlan()` 却认为所有标定都是 SWD，划掉真实 RISC-V 结果并忽略它。 |
| 推荐规则不一致 | 实际 `max(3, ceil(readUs × 1.15) + 1)`；按钮 tooltip 写 25% 余量；RISC-V 计划说明写 ≥1.5 倍。单字 3.17 µs 推荐 5 µs 尚可作为起点；36.6 µs 推荐 44 µs，达不到说明中的 54.9 µs。这些余量都是经验值。 |
| 多变量 RISC-V 回退误用 SWD 模型 | `applyRecPeriod()` 标定失败/失效时退到 `plan.bestUs`。8 个连续 u32 的 RISC-V 计划估计 36.52 µs，回退推荐却是 16 µs。不能把这个值作为 JTAG 推荐。 |
| 读量少算 | 模型按 `frameBytes` 收费，漏掉合并间隙和 4 字节对齐。两个 u32 地址相差 16 B，实际读取 20 B、输出 8 B，却与紧挨着的 8 B 用同一个估算。按现有系数分别漏算 SWD 3.348 µs、JTAG 11.52 µs。漏算量不是新真机耗时。 |
| 时钟模型不完整 | SWD 单字快路径按 MHz 拟合，但一般跨度仍使用固定 60 MHz 系数。JTAG 系数来自 09-30；10-05 探针块读收尾已减少扫描，不能认为旧系数适配全部当前配置。 |
| 失败标定也被接受 | 网页没有把非零 `err` 当作无效结果；探针提前退出仍回报请求的 iters。用少量失败前耗时除以 2,000，会生成虚假的高速度。 |
| 标定指纹不完整 | 只比较变量名、下拉时钟及后端。相同变量名换成新 ELF 地址仍被认为 fresh；离线调用实际生产方法已复现。未包含地址、宽度、实际时钟、DMI delay 和采样模式。 |

对于较新的探针，固定系数应只用作启动前粗估。可靠推荐应该来自当前计划实际标定，
再用完整采样器和主机端到端窗口验证；失败应明确失败，不能退成“零丢档”。

## 历史跳点：值错误、快照撕裂、丢拍分别看

### 1. 每 32 拍读成零：已定位、已修复的探针 bug

09-30 探针审查记录：旧 `riscv_jtag_hold_read()` 周期性调用普通 `dmi_read()`
检查 SBCS，普通读先排空 pending，而 pending 恰好是上一拍有效样本。
随后交付了 NOP 的零响应。

修复前 **42,408 个样本中 1,324 个违例，坏值全零**，约为样本数 / 32。
改为两次原生 posted 操作，保留样本并读取 SBCS 后：

- 100 µs 周期：32,488 个样本，0 违例。
- 5 µs 周期：619,008 个样本，0 违例。
- 单字 M0 约 3.17 µs，SBA 错误计数为零。

证据是探针仓库 `docs/代码审查报告.md` 的“第二轮处置结论”；回归脚本为
`script_test/riscv_pipe_integrity_test.py`。当前源码仍保留修复的 posted 检查逻辑。
本轮未重新确认板上运行固件与源码版本相同。

### 2. 多通道关系不一致：运行中快照撕裂

探针 `docs/web-handoff-riscv-scope.md` 保存了 32 B 多通道实测撕裂率：
按节拍约 8.9%，满速约 26.6%。这些比例来自历史交接记录，未找到对应原始采集文件，
不能把它们当作本轮或当前固件的重新测量。

多字读取期间目标更新了变量，一帧可同时包含更新前后的成员；64 位变量也可能跨两次
32 位读取而撕裂。noncache 解决可见性，不能使多个成员成为原子快照。
需要可靠关联关系时，应由目标写一个观察快照并提供版本校验，例如 seqlock；
双缓冲也必须定义发布顺序和读者有效性校验，单纯交替写两块内存仍不足以保证一致。

### 3. 网页启动残留/布局问题：已修复的网页路径

[scope-page.md](../scope-page.md) §6.3 记录：上一轮 4 B 帧残留被当成下一轮 26 B 帧，
前 100 多个样本出现垃圾值，时间倒退误认为 u32 回绕，速率甚至被算成 55 Hz。
现有代码使用 DEF 起跑线丢弃旧包，并按地址排序变量；这些不是当前高频硬件天花板。

### 4. 丢拍与时间轴偏差：仍需优化诊断

探针调度追不上会增加 dropped；没空闲 TX 包缓冲会增加 usb_drop。
两者都可能没有 seq 缺口。网页 `_finishStop()` 只检查 seq 缺口，造成误导。
旧 STAT / STATUS 的 USB 和读错误计数只有 16 位；网页尚未接入探针已有的 action 11
完整 32 位采样快照，长时间高损失会话的计数可能回绕。

包头只包含首样本时刻；没有逐拍时间戳或逐拍有效性位图。网页用相邻包间隔估算包内
周期，存储层又每 64 样本设时间锚点。包内不规则丢拍被插值摊平，不能据此精确定位
某一拍的丢失位置；绘图 X 坐标按样本索引排列，不能把屏幕间距当作严格连续时间。
这会影响时间测量和“跳变”的形状，但没有证据表明它凭空改变原始样本数值。

当前探针还有一个代码风险：`scope_sample_once()` 包满后，如果 `scope_pipe_flush()`
读失败，仍推送最后样本未成功回填的包，然后才报读错误。尾值可能是复用缓冲里的旧值，
没有逐样本无效标记。本轮未在真机注入并复现；优化前应补回归并避免把它提交为有效样本。

F103 A/B 原始日志在探针仓库
`docs/validation/2026-10-04/logs/eece893-on.log`、`eece893-off.log`；
DISCARD 对照在 `78cca1d-run.log`、`78cca1d-discard.log`。
H743 / HPM 的原始本机历史文件为网页 `tmp/campaign-result.json`、
`tmp/campaign-h743-local-repeat.json`、`tmp/hpm-campaign-result.json`；这些文件未纳入 Git。
本轮从原文件摘出的 20 行统计已保存进上述审计 JSON，保留原路径及 startedAt。
它们验证吞吐/计数，没有逐样本契约结果，不足以证明“高频所有值正确”。

旧 [真机基准测试.md](../真机基准测试.md) 将约 440 kHz 称为 0x83 线速天花板；
后来的 H743 WebUSB 已超过 480 kHz，因此不能把那一句当作通用硬上限。
4 B 帧、124 帧/512 B 包时，500 kHz DATA 流约 2.06 MB/s，另有 STAT 开销。
当前证据不支持“USB HS 理论线速就是这么低”。

探针只有 8×512 B TX 缓冲。理想情况下单字 400 kHz 仅覆盖
`8 × 124 / 400000 = 2.48 ms`；500 kHz 是 1.984 ms。
这是乐观上界，DEF/STAT、当前填充包和在飞包会占用余量。
网页的 3 条 4096 B 挂读有帮助，但不能等同于增加设备缓冲。
主线程暂停、驱动/USB 调度延迟都可能最终耗尽设备缓冲，需要分层实测才能区分。

## 优化顺序与验收

1. **先修正确性与可信诊断。** 拒绝失败标定；按实际后端、完整计划指纹、实际时钟/
   delay/模式判断有效性；修正读量模型和 RISC-V 回退；统一推荐说明，移除“保证零丢”措辞。
   接入 action 11，分别显示调度跳拍、USB 缓冲耗尽、读错误、DAP 让路、包序号缺口和入库溢出。
   对失败尾字禁止交付旧值，并对包内时间洞的可知程度作明确处理。
2. **做受控 A/B，再调整速率建议。** 保持目标固件、探针版本、地址、时钟/idle、线材相同，
   三层分别测 M0、完整采样器 DISCARD、WebUSB；比较短批次、绘图、原始录制、触发开关。
   从 3 / 2.75 / 2.5 / 2.25 / 2 µs 测 SWD；JTAG 从可靠的较慢档逐步收紧，
   多变量按真实读成本选档。先 5 秒筛选，再 30 秒×3；候选还要跨 179 秒 v2 回绕长跑。
   用完整计数器的稳定窗口差值，而不是启动到收尾总数；吞吐和每值契约同时验收。
3. **按结果优化瓶颈。** DISCARD 也跟不上：优化探针调度/读计划，研究有界 JTAG 批次；
   DISCARD 稳定、推流缓冲耗尽：测提交深度、设备队列与 USB 完成调度；
   原始接收稳定、绘图才出问题：再评估 Worker、分批 LOD、刷新频率和内存压力。
   多成员一致性另用目标观察快照，不能靠网页插值或隐藏坏点解决。

不建议先一味提高 JTAG 时钟、减少 idle 或掩盖异常样本；这会把性能问题变成值正确性问题。
目前可以确认的主要限制是：6800EVK 高频单字/多字首先受探针读取与调度约束；
SWD 单字更接近主机排空和探针服务共同约束。当前证据无法给出所有模式统一的最高无损率。
