### 3. 新增功能问题的复核证据与安全修法

### F08：自愈绕过锁，且失败后会清掉故障标记

- 位置：`app/rtt/dap-webusb.js:507–522`、`:986–998`、`:1175–1176`。
- **已复现**：读 A 持锁未完成时，读 B 在锁外进入 `_targetInit()`；自愈尚未完成，读 C 又进入读临界区。事件序列保存在 `N01-heal-bypasses-memory-lock`。
- `_targetInit()` 当前使用的是 `_transfer`、`_readMemOnce` 等私有路径，原注释“会走公开 readMem 因而必死锁”与当前实现不符。
- **额外确认**：自愈开始先清 `_faulted`，初始化抛错后只返回 false，未重新置故障标记。核验 `N01b` 返回 false 时 `_faulted` 仍是 false。
- 修改应让“检查是否需要恢复 → 恢复 → 本次访问”在同一互斥边界内完成；恢复失败明确保留故障。仅先 `await _lockChain` 不是充分互斥，新的请求仍可能随后插入。

### F09：接口恢复后的调试连接状态未失效

- 位置：`app/rtt/dap-webusb.js:472–492`、`:232–307`、`:541–566`。
- `_onXferTimeout()` 调用 `_claim()`；该路径会 `resync()`，后者发送 DAP_Disconnect。当前恢复分支没有重新初始化目标，也没有明确标记目标状态需恢复。
- **已核验控制路径**：使用假 USB reset／claim 执行实际 `_onXferTimeout()` 后，`_faulted` 仍为 false。另用源码核对真实 claim → resync → Disconnect 调用链。未做实板超时实验。
- 建议独立表示“USB 接口可用／目标调试会话待恢复”，或者在适用后端标脏并由 F08 的受控恢复处理。不能直接用“claim 成功”代表下一笔目标访问安全。

### F10：零进展块读返回全长零数据

- 位置：`app/rtt/dap-webusb.js:1103–1135`。
- **已复现**：请求 8 字节，底层报告 `count=0, words=[]`，实际方法返回长度为 8 的全零数组，没有错误。
- 已成功读到一部分后再出现零进展，也会将未填充尾部留下的零值作为完整读取返回。应报出请求地址、期望／实际条数和阶段，不能靠无限重试解决。

### F11：I2C 脚本结果污染命令表

- 位置：`app/i2c/view.js:779–792`、`:830`、`:863`、`:881–889`。
- **已复现实际视图方法**：脚本第 1 行读结果写入 `results[0]`，上一份命令表第 2 行的结果同时残留。
- 不能只在脚本入口清空 results：那样仍会把新的脚本结果错画进命令表。应携带来源与目标行标识，或使用独立结果集合，再分别渲染。

### F12：忽略未确认 resumed 的结果

- 位置：`app/dbg/riscv.js:604–630`，以及 `_waitResumed()`。
- **已复现实际 step 方法**：`_waitResumed()` 返回 false，随后 `waitHalted()` 立即成功，方法仍返回 `'step'` 并声明完成。
- 采纳的是“负面确认结果被忽略”，不是“PC 没变一定没有单步”。修复需覆盖正常高速单步、自循环、恢复运行失败、运行后未停止四种情形。

### F13：finally／清理覆盖首因

- SPI 转发：`app/spi-cdc/session.js:27–30`。STATUS 失败后 close 也失败，最终异常只剩 close 的错误；保留该 HID 引用是必要的，不应删除。
- 周期引擎：`app/core/bus-periodic.js:124`。主体错误在 finally 的 stop 失败后被覆盖。
- **两处均已故障注入复现**：原始错误不在最终异常及 cause 中。应同时记录两种错误，资源保持失败状态，并给出下一步恢复操作。

## 6. 第二份报告逐条裁决

“修正后采纳”表示问题方向有价值，但影响、严重程度或修法需要修改；“不成立”针对其具体机制和建议，不证明整个模块永远没有问题。

| 来源条目 | 裁决 | 依据／合并去向 |
| --- | --- | --- |
| 必修 #1 RTT `_bridgeRequested` 残留 | **不接受原修法；反馈部分采纳** | START 抛错不能证明固件没启动；fail 账本使 CDC 变为 unknown。定向核验中手动清 requested 后依然 unknown，不会解决阻塞。接收、记录和其他普通串口也不等于“全部哑掉”。保留占用，改善恢复说明，合并 D13。 |
| 必修 #2 SWD heal 锁外执行 | **属实，新增 F08** | 实际读调用已复现与锁内读交错；另外发现失败清故障标志的问题。 |
| 必修 #3 USB timeout 后未标待恢复 | **属实，新增 F09** | 控制路径及 claim → resync → Disconnect 已核对；修法要区分后端。 |
| 必修 #4 DMI/SBA 双队列互换响应 | **所述机制不成立** | `_sbaQueue` 串行整个内存事务，普通访问的 dmiRead/dmiWrite 仍进 `_dmiQueue`，批量 `_sbaBurst` 也使用 `_dmiQueue`。并发核验的 READ/NOP 对未被拆开，结果正确。机械统一队列反会使内存事务等待自身的 DMI 子调用而死锁。 |

## 11. SRAM 高速档定因与修复（2026-10-16，提交 1f27947）

详见 [定因报告](validation/20261016-sram-root-cause-134100/report.md)，run-id：`20261016-sram-root-cause-134100`。

**根因**：网页 `WebUsbDapProbe.abort()` 的 `DAP_WriteABORT` 请求漏了 DAP 索引字节，固件读到的 abort 值实际为 0 → sticky 错误永远清不掉；一次瞬态 AP 错误就把链路毒化，页面只能一路降档。实板对照（源码入口与 `index.html?modules=bundle` 发布包入口各一遍）：触发 FAULT 后 DP CTRL/STAT=`0xF0000020`，旧报文 `[8,30,0,0,0]` 不清位，新报文 `[8,0,30,0,0,0]` 变 `0xF0000000`；期间 Flash 与 17 个体系寄存器逐字节一致。

## 13. 正式版移除烧录页 SRAM 读写测速实验

此前 SRAM 测速作为一次性硬件实验入口，要求暂停目标并覆盖选定 SRAM，页面本身不备份/恢复原数据；最终复核又显示按 4 KiB TAR 分组的网页实现比原有访问路径慢，因此不纳入正式产品功能。正式版移除烧录页入口、测速专用实现及其专用测试；保留烧录算法所需的目标 SRAM 缓冲、通用调试内存访问、全局硬复位功能，以及本文件和 `docs/validation/` 中的历史实验记录。
